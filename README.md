# WeatherNext

A weather app built with [Next.js](https://nextjs.org/) (Pages Router), React, TypeScript, Tailwind CSS and MUI. It fetches current weather data from the [OpenWeather API](https://openweathermap.org/api).

## Getting Started

**Prerequisites:** Node.js and npm. This project uses **npm** as its package manager (do not use yarn).

1. Install dependencies:

```bash
npm install
```

2. Create a `.env` file in the project root with your OpenWeather API key:

```bash
NEXT_PUBLIC_WEATHER_KEY=your_api_key
```

3. Run the development server:

```bash
npm run dev
```

Open [http://localhost:3000](http://localhost:3000) with your browser to see the result.

## Architecture

The code is split into layers, each with one job:

| Layer | Location | Responsibility |
| ----- | -------- | -------------- |
| Service | `services/` | Calls the API and returns the data. Takes plain parameters and doesn't use React, hooks or translations. |
| Hook | `hooks/` | Holds the React state for a feature (data, loading, errors) and calls the services. |
| Component | `components/` | Renders the UI. Gets its translated text from `useTranslation()`. Its props are typed in a separate `Component.types.ts` file. |
| Types | `types/` | Types shared by more than one layer (e.g. `WeatherData`). |
| Page | `pages/` | Connects hooks and components and owns page-level UI state (e.g. the notification). |

Data flow for a search:

1. `Search` submits the form.
2. `pages/index.tsx` calls `getWeather(city)` from `useWeather`.
3. `useWeather` calls `getWeatherByCity(city, lang)` from `weatherService`, which returns a `WeatherData`.
4. `useWeather` updates `weather` (`WeatherData | null`) and `isLoading`, or sends a translated error message through its `onError` callback.
5. `pages/index.tsx` renders `Weather`, `Spinner` or `Notification`.

## Internationalization (i18n)

The app supports Spanish (`es-CO`, default) and English (`en-US`) using Next.js [built-in i18n routing](https://nextjs.org/docs/pages/building-your-application/routing/internationalization) and static JSON files. No i18n library is used.

### How it works

- **Routing:** locales are configured in `next.config.js`. Spanish is served at `/` and English at `/en-US`. `localeDetection` is enabled, so on the first visit users with an English browser are redirected to `/en-US`.
- **Translations:** `locales/<locale>.json` holds every UI string, plus `apiLang` (the language code sent to OpenWeather).
- **`useTranslation` hook** (`hooks/useTranslation.ts`) returns:
  - `t(key)`: the string for `key` in the current locale. `key` is typed as `TranslationKey` (the keys of `locales/es-CO.json`), so an unknown key is a type error.
  - `locale`: the active locale.
  - `toggleLocale()`: switches to the other locale with a client-side route change. There's no page reload, and page state is preserved.
- **Components** call `useTranslation()` themselves instead of receiving translated strings as props.
- **Weather data:** when the locale changes, `useWeather` fetches the last searched city again, so the weather description from the API matches the new language.

### Usage

```tsx
import useTranslation from "../../hooks/useTranslation";

const MyComponent = () => {
  const { t } = useTranslation();
  return <p>{t("humidity")}</p>;
};
```

### Adding a string

Add the same key to **every** file in `locales/`. Keys are typed from `locales/es-CO.json`, and the `translations` map requires every locale to have all of them, so a key missing from a locale is a type error.

### Adding a locale

1. Add the locale code to `i18n.locales` in `next.config.js`.
2. Create `locales/<locale>.json` with all existing keys, including a valid OpenWeather `apiLang`.
3. Add the locale code to the `Locale` type and register it in the `translations` map in `hooks/useTranslation.ts`.
4. `toggleLocale()` assumes there are exactly two locales. Replace it with a language selector.

See [docs/i18n-plan.md](docs/i18n-plan.md) for the implementation plan and the design decisions behind it.

## TypeScript

- `strict` mode is enabled in `tsconfig.json`.
- Component props live in `components/<name>/<Name>.types.ts`, not in the component file. Pages reuse those signatures, e.g. `const handleToClose: NotificationProps["handleToClose"] = ...`.
- Types used by more than one layer go in `types/`. `WeatherData` only types the API fields the app reads; add a field when a component starts using it.
- `next.config.js`, `tailwind.config.js` and `postcss.config.js` stay as JavaScript (`next.config.ts` needs Next 15+).

See [docs/typescript-plan.md](docs/typescript-plan.md) for the migration plan and its decisions.

## Guidelines

- Use **npm** only. Commit `package-lock.json`; do not add `yarn.lock`.
- Keep secrets in `.env` (git-ignored). Never commit it.
- Place reusable UI in `components/`, each component in its own lowercase folder with a PascalCase `.tsx` file and, if it has props, a `.types.ts` file. Routes go in `pages/` (`.tsx`).
- Put API calls in `services/` and stateful logic in `hooks/` (`useXxx.ts`). Keep pages focused on wiring them together.
- Put types shared across layers in `types/`. Avoid `any`; use `import type` for type-only imports.
- Style with Tailwind utility classes; use MUI components where already established.
- Never hardcode UI text. Add it to every file in `locales/` and read it with `t()` from `useTranslation`.
- Follow the existing code patterns, and keep changes scoped to what the task requires.
